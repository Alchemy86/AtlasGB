**Every address in Pokémon Red and Blue, what lives there, and — for almost all of them —
evidence that we watched the cartridge use it.**

This is **one atlas** in [AtlasGB](../../README.md), which is a project for mapping Game
Boy cartridges with the evidence attached. It is the first one. Everything below is about
**Pokémon Blue and Pokémon Red, English (USA/Europe)** and nothing else; another cartridge
gets [its own atlas](../../docs/adding-an-atlas.md), never a merge into this one.

## The evidence

<!-- atlas:begin (evidence) — generated by tools/render.py from the atlas data; edit the data, not the table -->

| evidence | entries | what it means |
|---|---:|---|
| **R** — the cartridge names it | 1,594 | the address appears as the operand of an instruction in the ROM image |
| **L** — observed live | 2,694 | the byte changed while the cartridge ran a fixed script on this emulator |
| **I** — an invariant covers it | 36 | a named check proved it means what the atlas says it means |
| *(none)* | 7 | no evidence yet — stated, not hidden |

Storage entries in total: **2,842**.

Written descriptions cover **628 of the 1,012 distinct addresses** (62%). The rest carry their symbol name and their evidence and nothing more, which is the honest state of them — every chapter page reports its own figure at the top of its table.

<!-- atlas:end (evidence) -->

An entry can carry more than one tier, so those numbers overlap. What none of them can do
is more interesting than what they can:

- **R** is a byte scan, not a disassembly, so a single hit is weak — but it cannot produce
  a false *negative*.
- **L** only marks what one fixed script touched, and that script never reaches a battle
  or a PC. **An unmarked entry means "not observed", never "not used".**
- **I** is the only tier that can catch an address which is real, live, and describing the
  wrong thing — and an invariant is only as strong as the save it runs against. The ones
  that can pass vacuously [say so](../../docs/verification.md#i--an-invariant-covers-it)
  instead of reporting a pass they have not earned.

**Those counts are over storage entries only** — video RAM, cartridge RAM, work RAM, high
RAM. Counting the cartridge's own data tables in as well moves **I from 36 to 39**, because
three ROM-table labels (`MonsterNames`, `BaseStats`, `PokedexOrder`) carry an invariant
too. Both figures are recorded in [`data/evidence.json`](data/evidence.json), under
`evidence` and `evidence_including_rom_tables`, so neither can be quoted as the other. The
table above is the storage figure, because "observed live" means something different for a
table that never changes.

**The tiers cannot go stale.** They are written by landing a verification run, never by
hand, and CI checks that the evidence column is still the one the last landed run
produced. A tier here always names a real run against a real cartridge, identified by
commit and by the cartridge's SHA-1.

## No holes

<!-- atlas:begin (coverage) — generated by tools/render.py from the atlas data; edit the data, not the table -->

| region | span | bytes | named by a symbol | reached by no label | unallocated |
|---|---|---:|---:|---:|---:|
| Video RAM | `$8000-$9FFF` | 8,192 | 8,192 | 0 | 0 |
| Cartridge RAM bank 0 | `$A000-$BFFF` | 8,192 | 6,232 | 0 | 1,960 |
| Cartridge RAM bank 1 | `$A000-$BFFF` | 8,192 | 3,980 | 1,432 | 2,780 |
| Cartridge RAM bank 2 | `$A000-$BFFF` | 8,192 | 6,739 | 0 | 1,453 |
| Cartridge RAM bank 3 | `$A000-$BFFF` | 8,192 | 6,739 | 0 | 1,453 |
| Work RAM | `$C000-$DFFF` | 8,192 | 7,908 | 255 | 29 |
| High RAM | `$FF80-$FFFE` | 127 | 127 | 0 | 0 |

<!-- atlas:end (coverage) -->

**Work RAM and high RAM are 100% accounted for — 8,192 of 8,192 and 127 of 127.** Every
byte is named by a symbol, or inside a section no label reaches, or declared unallocated
by the linker.

That matters more than it sounds. **A hole in a memory map is a byte nobody looked at**,
and every other Gen 1 map is full of them — not marked as unknown, just absent, so you
cannot tell "nothing is here" from "nobody checked". A tool that writes into a hole
corrupts something it cannot name.

The `gap` and `free` rows are what make it add up, and the one gap in work RAM is a good
example of why they exist: the `Stack` section is `$DF00-$DFFF` and its only label sits at
`$DFFF`, because the stack pointer starts at the top and grows *downwards*. Those 255
bytes are honestly "reached by no label" rather than missing.

Cartridge RAM's four banks are sparse on purpose — bank 0 is a scratch buffer, bank 1 is
the save, banks 2 and 3 are the stored Pokémon boxes — and the unallocated remainder of
each is real spare room on the cartridge, not a gap in this map.

## One entry, in full

Every row of [`data/atlas.tsv`](data/atlas.tsv) looks like this. Ten tab-separated
columns, no quoting, no escaping — [the schema](../../docs/schema.md) is the full contract,
and it is shared by every atlas in the project.

<!-- atlas:begin (example) — generated by tools/render.py from the atlas data; edit the data, not the table -->

```text
region	bank	addr	len	symbol	role	sect	group	verify	desc
WRAM0	-	$D163	1	wPartyCount	entry	Party Data	party	rom,live,inv	How many Pokemon you are carrying, 0 to 6. **Verified live**: the harness reads it, walks both parallel species lists, and requires them to agree and to be `$FF`-terminated.
```

| column | value | what it means |
|---|---|---|
| `region` | `WRAM0` | which of the CPU's address ranges it is in |
| `bank` | `-` | the bank, or `-` where the region is not banked |
| `addr` | `$D163` | the CPU address, `$` then four uppercase hex digits |
| `len` | `1` | bytes this symbol owns before the next named address |
| `symbol` | `wPartyCount` | the label, as the disassembly spells it |
| `role` | `entry` | `entry`, `alias`, `instance`, `gap` or `free` |
| `sect` | `Party Data` | the linker section it was declared in |
| `group` | `party` | our chapter — [`tools/chapters.py`](../../tools/chapters.py) decides it |
| `verify` | `rom,live,inv` | the evidence, comma separated: `rom`, `live`, `inv` |
| `desc` | How many Pokemon you are carrying, 0 to 6. **Verified live**: the harness reads it, walks both parallel species lists, and requires them to agree and to be `$FF`-terminated. | what it is, in our own words — empty when nobody has written one |

So `wPartyCount` carries **RLI**: the cartridge names this address as an instruction operand; the byte changed while the cartridge ran the fixed script; a named invariant proved it means what it says.

<!-- atlas:end (example) -->

Its permanent links are [`docs/party.md#s-wPartyCount`](docs/party.md#s-wPartyCount) and
[`docs/by-address.md#a-D163`](docs/by-address.md#a-D163). Anchors are derived from the
symbol and the address, so they survive regeneration and are safe to link to from
elsewhere.

## What this atlas covers, and what it does not

**Pokémon Blue and Pokémon Red, English (USA/Europe).** The disassembly builds both from
one source and the work RAM map is shared, so every address here is Red's too. The
differences are in ROM data — which Pokémon appear where, a handful of tables — and not in
where anything lives.

**Yellow is deliberately out of scope and is not approximated.** Its work RAM shifted, so
an address from here is *wrong* there rather than approximately right, and the failure
mode is a write landing in the middle of somebody else's data and passing its own
checksum. Yellow needs its own build, its own extraction and its own verification run —
and, in this layout, its own directory beside this one. The machinery would do it;
[nobody has](../../docs/adding-an-atlas.md).

**Generation 2 is not covered.** Different engine, different map, and so a different
atlas.

**No ROM data of any kind is here, and none is fetched.** The cartridge's own tables appear
as *addresses*; the numbers at them are read out of the player's own cartridge at run
time. See [licence](../../docs/licensing.md).

## Contributing to this atlas

The two things that would help most, in order:

1. **A second live script.** The current one plays the opening and then walks and opens
   menus, so it never reaches a battle or a PC. Measured directly (2026-08-25): only **7**
   storage entries currently have no evidence at all, so a battle-and-PC script would move
   a handful of specific bytes, not hundreds — but it is still the highest-value single
   change available, because those 7 are exactly the ones nothing else can reach, and
   closing them completes the storage evidence entirely. [The machinery
   exists](../../docs/verification.md#confirmed-against-the-cartridge-independently-on-2026-08-25);
   only the script is missing.
2. **Descriptions.** 628 of 1,012 distinct addresses carry one. The rest are honest but
   thin. Write from scratch, from real evidence — a disassembly symbol, a measured finding,
   observed behaviour under the emulator — never from the plausibility of the symbol name
   alone; see [provenance](../../docs/provenance.md) for why that matters — and hedge
   anything an invariant does not cover. When the well of already-written-down evidence runs
   dry, [generating fresh evidence by watching a real playthrough](../../docs/observation.md)
   is what closed the next ninety.

Then: `make check` before you push. It is what CI runs, and it is red until every
generated file agrees with the data.

```bash
make check                    # everything CI runs, for every atlas
make docs ATLAS=pokemon-rb    # regenerate just this atlas's pages
make data ATLAS=pokemon-rb    # regenerate just this atlas's JSON
```

**The seven unevidenced entries stay marked as unevidenced.** That honesty is the product.
A pull request that quietly upgrades one without a verification run behind it will be
turned down, and CI will catch it first.

Want to map a *different* cartridge? That is [adding an atlas](../../docs/adding-an-atlas.md),
not a change to this one.
