# Graphics — Pokémon Red/Blue

[← Pokémon Red/Blue](../README.md) · [by address](by-address.md) · [by name](by-name.md) · [the structures](structures.md) · [AtlasGB](../../../README.md)

Video RAM's three tile blocks and two tilemaps, plus the working state of the thing that fills
them.

The font block is the one that makes [the screen readable as text](screen.md). `vTileset` is
the 96 background tiles a map's tileset copies in, re-copied on **every** map load — so
anything a tool writes there is clobbered at the next door, which is a thing worth discovering
from a page rather than from an experiment.

**Gen 1 stores its Pokémon pictures compressed**, and decompresses them into three buffers in
*cartridge RAM* — a good reminder that battery-backed RAM is not only for saves. The format is
a **bit** stream, not a byte stream: a run-length code over two bitplanes, with an optional XOR
of one plane against the other, which is why the same picture can be encoded three ways and the
encoder picks whichever is smallest. The decompressor's whole working state is on this page —
input pointer, output pointer, which bit of which byte, which of two nybble-expansion tables is
current, and the flags that say how the planes combine.

[TerminalGB](https://github.com/Alchemy86/TerminalGB) implements that format
(`plugins/trainer/src/sprite.rs`) and proved it byte-identical to the disassembly's own output
for thirteen species covering every picture bank and both special cases. **The pictures
themselves are read out of the player's cartridge at run time and appear in neither
repository.**
