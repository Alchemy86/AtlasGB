# The dice

[← AtlasGB](../README.md) · [by address](by-address.md) · [by name](by-name.md) · [the structures](structures.md)

Four bytes, and the most important fact about them is what they *cannot* give you.

`Random_` is two three-instruction sequences, and each one folds **`rDIV`** — the hardware
divider register, which counts continuously and is not part of the game's state — into the
seed. So a Gen 1 roll is not reproducible from the seed: it depends on when the call happened,
to the cycle. You cannot fix an individual roll by writing the seed.

What *is* reproducible is a whole run: emulation is deterministic, so the same starting state
plus the same script gives bit-identical frames. That is the difference between "make this
Pokémon shiny" (impossible) and "produce this clip again" (routine), and it is why a shiny hunt
has to decorrelate its machines by *time* rather than by seed.

`BattleRandom` is `Random` **except in a link battle**, where it draws from a nine-entry list
both consoles share, advanced by a pure `x*5+1` with no divider in it at all. Both consoles
must roll identically for a link battle to stay in step, which is exactly why it cannot use the
hardware clock.

One consequence that catches people: because both DV bytes of a wild Pokémon come from two
`Random` calls microseconds apart, they are **not independent** — reload the same save state
and roll again and the results land on a thin one-dimensional band, a few hundred of the 65,536
possible spreads. That is measured, and it is why [shiny hunting](https://github.com/Alchemy86/TerminalGB/blob/main/docs/shiny-hunt.md) has to
run a battle between attempts.
